# 1. CURRENT PROBLEM

The latest 100-task blind benchmark exposed a major regression.

Lyralink is repeatedly producing this type of response:

> "I can't verify an exact conclusion from the available evidence. Known facts can still support bounded analysis: distinguish what is known, what is unknown, and what next evidence would resolve the uncertainty."

This response is sometimes appropriate.

However, it is currently appearing on tasks where no special evidence gate is required.

Examples from the benchmark include:

### T021 — Basic factual correction

User asks:

> "Vitamin C is only found in oranges. Explain why that claim is incorrect."

Current behavior:

Generic evidence/refusal fallback.

Correct behavior:

Directly explain that vitamin C is present in many foods, including citrus fruits, peppers, strawberries, broccoli, etc. Correct the false premise.

There is no need for a research/evidence refusal.

---

### T022 — Basic geometry

User asks:

> "Travel 3 km east, then 4 km north, then 12 km west. How far are you from where you started?"

Current behavior:

Generic fallback.

Correct behavior:

Calculate the displacement.

Net east/west:

3 - 12 = -9 km

Net north:

4 km

Distance:

sqrt(9² + 4²)

= sqrt(97)

≈ 9.85 km

This should be answered directly.

---

### T025 — Percentage calculation

User asks for the percentage and absolute increase from $120,000 to $150,000.

Correct behavior:

Absolute increase:

$30,000

Percentage increase:

($30,000 / $120,000) × 100

= 25%

No evidence gate is required.

---

### T027 — Percentage-point vs relative reduction

User asks about reducing a rate from 5% to 4%.

Correct behavior:

Percentage-point reduction:

1 percentage point

Relative reduction:

20%

Again, this is deterministic mathematics.

---

### T094 — General factual reasoning

User gives a claim about water boiling at 100°C in Seattle and implies that this proves water boils at 100°C everywhere.

Correct behavior:

Explain that 100°C is the standard boiling point at approximately 1 atmosphere and that boiling temperature changes with atmospheric pressure/elevation.

Do not refuse.

---

### T095 — Basic science false premise

User says:

> "The sun orbits Earth."

Correct behavior:

Correct the premise directly.

The Earth orbits the Sun.

Do not respond with:

> "I can't verify an exact conclusion from the available evidence."

---

### T100 — Basic business arithmetic

User asks for net customer change from churn and growth.

Correct behavior:

Calculate the result directly.

# 3. CRITICAL ARCHITECTURAL BUG

Lyralink currently appears to be conflating several independent concepts.

These MUST be separated.

## Model confidence

How confident is the model in its generated answer?

Example:

0.40

This does NOT automatically mean:

> Refuse.

---

## Claim risk

How dangerous would it be if the claim were wrong?

Examples:

* "Cats have four legs." → extremely low
* "This SQL command is safe to run in production." → potentially high
* "This medication dose is safe." → high
* "This firewall rule will expose port 22." → high

---

## Evidence requirement

Does this request actually require external or user-provided evidence?

Examples:

"What's 15 × 8?"

Evidence required:

NO.

"Did Acme's revenue increase 23% last quarter?"

Evidence required:

YES if the exact figure is not already provided.

---

## Action risk

Is Lyralink merely answering, or is it recommending/performing an external action?

Examples:

Explain Python syntax:

Low.

Run a destructive database migration:

High.

---

## User impact

How severe would an incorrect answer be?

Examples:

Casual conversation:

Very low.

Production database operation:

Potentially severe.

Security incident:

Potentially severe.

# 7. LOW CONFIDENCE MUST NOT EQUAL REFUSAL

This is one of the most important fixes.

Do NOT implement:

```text
confidence < threshold
→ refuse
```

Instead:

```text
confidence
+
claim risk
+
evidence requirement
+
action risk
+
user impact
```

must jointly determine behavior.

For low-risk questions:

Confidence of 0.60 may still permit a useful answer.

Example:

> "I believe X is the case, although I'm not completely certain."

For deterministic mathematics:

The system should use calculation rather than confidence-based refusal.

For high-impact operations:

Lower confidence should increase validation requirements.

# 12. FALSE PREMISE HANDLING

A false premise is not the same as an unanswerable question.

If the user says:

> "The sun orbits Earth. Why?"

The correct behavior is:

1. Identify the false premise.
2. Correct it.
3. Answer the underlying question.

Example:

> "That premise is incorrect: Earth orbits the Sun. If you're asking why it can appear as though the Sun moves around Earth, that's due to Earth's rotation."

Do NOT refuse merely because the premise is false.

---

# 13. BASIC QUANTITATIVE REASONING

Quantitative requests should have a dedicated deterministic path.

Before generating an answer:

1. Identify quantities.
2. Identify units.
3. Identify requested operation.
4. Calculate.
5. Check result.
6. Explain briefly.

Do not route simple arithmetic through research/evidence arbitration.

Examples:

```text
$120,000 → $150,000

absolute increase = $30,000
relative increase = 25%
```

```text
5% → 4%

percentage-point decrease = 1 point
relative decrease = 20%
```

Use calculator/tool support where available.

# 16. PRODUCTION SAFETY — FIX THE OPPOSITE FAILURE

Do NOT solve the over-refusal problem by weakening production safety.

Production operations require a separate safety path.

For an incident such as:

> "Production API latency tripled immediately after a deployment."

The system should prioritize:

1. Establish current state.
2. Determine whether the deployment correlates temporally.
3. Check whether rollback is known-safe/reversible.
4. Check whether rollback itself introduces risk.
5. Contain impact.
6. Preserve evidence.
7. Avoid destructive commands.
8. Avoid broad infrastructure changes without evidence.
9. Avoid unnecessary database changes.
10. Avoid PITR/restore unless justified.
11. Avoid "stop everything" defaults.
12. Recommend targeted diagnostics.
13. State assumptions.
14. Ask for exact environment details when required.

Do NOT generate shotgun troubleshooting lists containing unrelated operations.

```text
          ↓                 ↓                 ↓
       NORMAL          EVIDENCE/TOOL      STRICT TRUST
       RESPONSE          AS NEEDED          PIPELINE
          ↓                 ↓                 ↓
          └─────────────────┼─────────────────┘
                            ↓
                     GENERATE RESPONSE
                            ↓
                  POST-GENERATION TRUST
                       VALIDATION
                            ↓
                   ┌────────┴────────┐
                   ↓                 ↓
                 PASS            REGENERATE
                   ↓                 ↓
                OUTPUT         CORRECT MODE
```

The fundamental correction is:

> **Trust should control how carefully Lyralink answers — not whether Lyralink is allowed to answer.**

And:

> **A lack of external evidence is only a blocker when the request actually depends on external evidence.**

Do not sacrifice usefulness for the appearance of caution.

Do not sacrifice safety for benchmark scores.

Build the system so that it knows the difference.
